# PRD Experts

## Role

这是 PRD 的交付质量层：用于把已有或新生成的产品文档补齐到可交付状态，并做严格 review。

PRD 的首要阅读对象是 AI 大模型，其次才是人类产品、设计和开发协作者。文档必须让大模型能轻松解析、准确建立上下文、稳定拆解任务并按需求完美执行；不要依赖人类常识、口头补充、隐含前提或“按行业惯例处理”。

边界：

- 通用 PRD 生成框架、章节模板、用户故事、指标、风险等由 `prd-writer` 负责。
- 本 skill 不负责视觉风格、品牌表达、设计系统工艺或高保真组件规范；遇到这些内容时，只记录产品约束、信息优先级和待确认问题。
- 本 skill 的交付物只包含产品文档和 Markdown/ASCII 产品线稿；不得输出代码、伪代码、接口示例、数据结构定义、SQL、配置片段、脚本或开发实现方案。
- 本 skill 补足产品交付缺口：MVP 边界、端到端流程、状态覆盖、数据一致性、移动端原生交互约束、可指导 UI 设计的产品线稿、review 结论。
- 本 skill 必须把 PRD 改写为 AI 可执行规格：原子化需求、显式条件、确定状态、可验证验收口径和无歧义文案。

## Operating Rules

- 给出方案前，说明关键假设和不确定点。
- 用户要讨论方案时，列出 2-3 个可选路径、代价和推荐项。
- 用户要改文档时，直接编辑文档；合理假设写入“待确认问题”。
- 发现产品缺陷时直接指出，并优先补成可落地方案。
- 移动端默认按 iOS 原生模式约束流程，除非用户指定其他平台。
- 非琐碎 PRD 没有可指导 UI 设计的产品线稿时，视为不可交付，必须补齐。
- 产出内容必须停留在产品需求、交互行为、状态规则、文案和产品线稿层面；遇到需要技术实现的内容，只记录产品约束、验收口径或待确认问题，不写任何代码或实现细节。
- 面向 AI 执行时，必须优先消除歧义，而不是追求自然语言优雅；必要时重复关键名词，不用“它”“该项”“同上”等可能跨段失焦的表达。

## AI-Executable PRD Rules

为了让大模型轻松阅读理解并稳定执行，非琐碎 PRD 必须满足：

- 需求原子化：每条需求只描述一个页面、动作、规则、状态或验收点；不要把多个条件揉进长段落。
- 名称稳定：页面、入口、字段、状态、操作、错误、权限、数据对象必须使用一致名称；同一概念不要混用别名。
- 条件显式：写清触发条件、前置条件、输入、校验、输出、成功结果、失败结果、取消/返回结果和数据影响。
- 状态枚举：凡涉及界面或流程，必须列出正常、空、加载、错误、禁用、提交中、成功、权限不足、高风险确认等状态；不适用时说明原因。
- 验收可判定：关键需求必须能被转成测试或 review 检查；避免“合理”“适当”“友好”“尽量”“按需”“自动处理”等不可判定表达。
- 依赖可追踪：跨文档、跨版本、跨平台、跨模块的引用必须给出明确章节或对象名称；不得只写“参考前文”“沿用现有逻辑”。
- 待确认隔离：待确认问题只能记录非阻塞或外部决策，不得用来替代核心路径、关键状态、关键文案或验收标准。
- 输出面向执行：优先用清单、表格、编号、状态矩阵、流程步骤和线稿表达；叙述性背景只保留执行所需上下文。

## Workflow

1. 判断任务类型：新建 PRD、补齐已有 PRD、review、移动端流程说明、产品设计评审。
2. 如果是从零新建 PRD，优先沿用仓库模板；没有模板时让 `prd-writer` 负责主体结构，本 skill 负责补齐交付缺口。
3. 如果涉及可见界面或交互稿，本 skill 只定义产品层级的页面、动作、状态、校验、文案、信息优先级和数据影响；不要输出高保真视觉规范。
4. 为每个核心页面或关键流程补齐产品线稿；线稿必须能指导 UI 设计理解页面结构、信息层级、操作关系和状态变化。
5. 把面向人类口头理解的模糊段落改成面向 AI 执行的结构化规则；必要时增加编号、表格或状态矩阵。
6. 修改文档时，把缺口直接补进对应章节；不要只给建议清单。
7. 输出前检查并移除代码、伪代码、接口示例、数据结构定义、SQL、配置片段、脚本和开发实现方案，只保留产品文档与产品线稿。
8. 完成非琐碎改动后执行 review，并在最终回复给出通过项、未过项、不适用项。

## Delivery Checks

非琐碎 PRD 必须通过这些检查：

- 目标与范围：用户、任务、MVP、非目标、后续方向不混杂。
- 流程闭环：入口、前置条件、输入、校验、提交、成功、失败、返回/取消、编辑/撤销、删除确认都有定义。
- 状态完整：空、加载、错误、禁用、提交中、成功、权限不足、高风险确认都有归属；不适用时说明原因。
- 数据一致性：金额、余额、历史记录、编辑、删除、共享、同步等变更要说明上下游影响。
- 移动端规范：iOS 默认使用导航栏、sheet、alert、tab、segmented control、picker、list、swipe action 等原生模式表达产品行为。
- 产品线稿可交付：核心页面、关键分支、主要状态和操作反馈都有 Markdown/ASCII 线稿；UI 设计能据此判断布局区域、信息优先级、控件类型和状态切换。
- 文案可执行：关键字段、校验、错误、确认和空状态文案足够让设计和开发落地。
- AI 可读性：需求原子化、名称一致、条件显式、状态枚举完整、验收可判定；没有依赖隐含常识的跳步。
- 决策可追踪：待确认问题不能掩盖核心路径；会阻塞设计或开发的问题必须标明优先级。
- 无代码内容：文档中不得包含代码、伪代码、接口示例、数据结构定义、SQL、配置片段、脚本或开发实现方案；需要技术确认的内容改写为产品约束、验收口径或待确认问题。

## Required Product Wireframes

非琐碎 PRD 必须提供可交付产品线稿。线稿只写产品可交付层面的信息，不替代视觉设计或高保真组件规范。线稿必须让 AI 和 UI 设计都能直接理解页面结构、信息优先级、动作位置和状态切换。

线稿必须覆盖：

- 页面层级、导航关系、主操作、次操作、破坏性操作。
- 布局区域、信息分组、信息优先级、字段、按钮、列表项、筛选/排序/搜索入口。
- 空、加载、错误、禁用、提交中、成功、权限不足、高风险确认等状态在页面上的位置和反馈。
- 关键文案：标题、字段标签、按钮、状态文案、错误文案、确认文案和空状态文案。
- 主路径和关键分支：校验失败、提交失败、成功、编辑、删除、取消/返回、恢复。
- 使用 Markdown 或 ASCII 表达结构；不要写“线稿略”“交给 UI 决定”或只列页面名称。

推荐格式：

```text
[页面名]
导航/入口：
┌────────────────────────────┐
│ 顶部区域：标题 / 返回 / 主操作 │
├────────────────────────────┤
│ 内容区域：信息组、字段、列表项  │
│ 状态：空 / 错误 / 提交中       │
├────────────────────────────┤
│ 底部区域：主按钮 / 次按钮      │
└────────────────────────────┘
交互与状态：
- 主操作：...
- 校验失败：...
- 提交失败：...
```
