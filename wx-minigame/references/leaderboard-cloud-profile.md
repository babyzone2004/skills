## 适用场景

实现或排查以下问题时使用本参考：
- 排行榜、共修榜、小组榜、分数榜、连击榜。
- 微信云函数、共享云环境、跨 App 云资源访问。
- 头像昵称授权、资料编辑、资料保存后刷新或重启回退。
- 相册选择头像、云存储上传、隐私授权失败。

## 一次性实现完整排行榜功能

做排行榜时不要只做“列表能显示”。一次完整交付至少包含以下闭环：

1. **入口与 UI**：首页入口、排行榜弹窗、Tab、刷新、加载/失败/空态、我的排名/本机兜底、资料按钮。
2. **榜单类型**：明确每个榜单的字段、排序、Top N 缓存、当前用户排名计算方式；例如连击榜用 `maxCombo`，小组榜用小组累计值。
3. **用户资料**：定义 `LeaderboardProfile`，至少包含 `nickname`、`avatarUrl`、`updatedAt`。所有榜单行都能展示头像，缺头像时画空头像。
4. **授权资料编辑**：实现资料弹窗、微信头像授权、昵称编辑、保存按钮、保存中状态、错误提示。
5. **云函数**：实现 update/get 两条主路径；update 写用户主表并 best-effort 刷缓存，get 读缓存/重算并返回当前用户资料。
6. **本地一致性**：保存成功后立刻更新 UI、本地缓存和当前用户行；刷新拿旧缓存时不能覆盖刚保存资料。
7. **部署说明**：列出云函数名、集合名、环境、索引、构建命令、需要重新部署哪些云函数。
8. **真机验收**：首次授权、已授权再次编辑、手动昵称、保存后刷新、关闭重开、榜单空缓存、云函数失败都要跑。

推荐实现顺序：

```
接口类型 -> 云函数与集合 -> 平台 service -> Canvas 榜单 UI -> 资料编辑 UI
-> 微信授权按钮覆盖 -> 本地缓存/updatedAt 仲裁 -> 部署和真机验收
```

## 授权资料获取流程

微信小游戏的头像昵称获取要按“Canvas 自绘 + 原生透明按钮 + 手动编辑兜底”设计，不要依赖 DOM 或一次性授权魔法。

### 数据模型

客户端和云端都使用同一 profile 结构：

```ts
interface LeaderboardProfile {
  nickname: string
  avatarUrl?: string | null
  updatedAt?: number
}
```

云端用户主文档建议同时保留：
- `leaderboardProfile.nickname`
- `leaderboardProfile.avatarUrl`
- `leaderboardProfile.authorized`
- `leaderboardProfile.updatedAt`
- 兼容字段 `userName`、`avatarUrl`（如果旧逻辑或其它榜单读取它们）

### 打开资料弹窗

打开资料弹窗时按这个优先级填草稿：

1. 云端 `userProfile`。
2. 当前用户排名里的 `nickname/avatarUrl`。
3. 本地确认保存缓存。
4. 空草稿。

注意：
- 已有草稿时，静默微信资料预填只能补空字段，不能覆盖用户刚输入的昵称。
- 资料弹窗关闭时必须隐藏原生透明按钮，避免拦截 Canvas。

### 首次授权：透明 createUserInfoButton

Canvas 没有 DOM，首次授权要用原生按钮覆盖自绘头像区域：

1. 每帧或每次布局变化后，从资料弹窗拿到头像区域 rect。
2. 未授权且弹窗可见时，调用 `wx.createUserInfoButton({ type: 'text', text: '', style: transparentRect })`。
3. `onTap` 中从 `res.userInfo` 或 `res.rawData` 解析 `nickName/avatarUrl`。
4. 成功后填入资料草稿，提示“点击保存后同步排行榜”。
5. 授权成功、弹窗隐藏、切换页面或层级遮挡时，立即 `hide()` 或 `destroy()` 原生按钮。

透明按钮只覆盖头像区，不要覆盖昵称行；否则用户点击昵称会被按钮吞掉，无法编辑。

### 已授权后再次编辑

已授权不代表不能改：
- 点击头像仍要有响应。可以弹出菜单，只保留“使用微信头像”，相册入口如未稳定可注释隐藏。
- 已授权时可尝试 `wx.getUserInfo({ withCredentials: false })` 刷新头像昵称；失败时不要阻断手动昵称编辑。
- 点击昵称始终走手动编辑，例如 `wx.showModal({ editable: true })`，确认后把最新输入写入草稿。
- 保存时读取当前草稿，不要读取旧闭包里的昵称。

### 保存资料

保存按钮流程：

1. 校验昵称非空并截断长度。
2. 调用排行榜 update service，携带 `nickname/avatarUrl`，同时附带本机当前排行值（如 `maxCombo`）。
3. service 返回时，昵称以本次提交为准；头像用返回值或本次提交值兜底。
4. 写本地缓存 `{ profile, savedAt }`。
5. 更新 `currentProfile`、我的排名行、Top N 中当前用户行。
6. 关闭资料弹窗并刷新榜单；刷新结果如果比本地保存旧，不得覆盖本地资料。

### 启动和刷新回填

启动时：
- 先读取本地 profile cache 并应用到 UI。
- 再请求云端榜单和用户资料。
- 如果云端 `updatedAt` 更新，接受云端并刷新本地缓存。
- 如果云端缺 `updatedAt` 或比本地旧，保留本地短期权威。

这个流程专门解决“保存成功，重新打开又变回旧昵称/旧头像”的真机问题。

## 总体原则

1. **环境先行**：客户端初始化的云环境、云函数部署环境、集合所在环境必须一致。共享云环境下，客户端一般要用 `wx.cloud.Cloud({ resourceAppid, resourceEnv })` 创建云实例，云函数内仍用 `cloud.DYNAMIC_CURRENT_ENV`。
2. **命名明确**：跨项目共享云环境时，云函数名和集合名建议加项目唯一前缀，例如 `wood_leaderboardUpdate`、`wood_user_data`，避免不同小游戏相互污染。
3. **写主表，缓存降级**：用户资料与排行值写入用户主集合；排行榜缓存集合只作为加速层。缓存写失败只打日志，不应让保存资料或上传分数失败。
4. **客户端有短期权威**：保存资料成功后，本次提交的昵称/头像应立即成为 UI 短期权威，并写入本地缓存。榜单刷新拿到旧缓存时不能覆盖刚保存的资料。
5. **真机优先**：头像昵称授权、隐私协议、相册选择、云存储临时 URL 这些问题经常开发者工具正常、真机失败，必须按真机反馈设计降级。

## 云环境与 openid

共享云环境的常见坑：
- `OPENID` 可能是资源方/当前云环境视角，`FROM_OPENID` 才是调用方用户。云函数里取当前用户时优先使用 `wxContext.FROM_OPENID || wxContext.OPENID`。
- 客户端 `native` 云环境和共享云环境的函数、集合完全不同。保存成功但下次读不到，经常是 update 和 get 打到了不同环境。
- 部署时要同时确认：云函数已部署、集合已创建、集合名前缀一致、读写权限/索引满足查询。

建议云函数返回调试字段只在开发期使用，不要把 openid 等敏感值长期暴露给客户端。

## 云函数设计

排行榜更新函数建议职责：
- 校验 openid。
- upsert 用户主文档，例如 `user_data/{openid}`。
- 同时写入排行值（如 `maxCombo`）和 `leaderboardProfile`。
- 写入 `updatedAt` 与 `leaderboardProfile.updatedAt`。
- best-effort 刷新排行榜缓存。
- 返回 `{ success, value, profile }`，其中 `profile` 带 `updatedAt`。

排行榜读取函数建议职责：
- 普通打开优先读缓存。
- `forceRefresh` 时重算 Top N。
- 重算失败时回退缓存。
- 重算结果为空但旧缓存非空时回退旧缓存，避免索引/权限/环境问题让刷新后空榜。
- 单独读取当前用户资料和当前用户排名，不能只依赖 Top N 缓存。

保存资料时，云函数应允许只更新资料，也应允许资料和分数在同一次调用中更新。这样用户改头像昵称时，当前榜单行也能被刷新。

## 客户端一致性策略

资料保存成功后这样处理：
- 以本次提交的 nickname 为准，不要盲信云函数返回的旧 nickname。
- avatarUrl 使用云函数返回值或本次提交值兜底。
- 写本地缓存，例如 `leaderboard_profile_cache_v1 = { profile, savedAt }`。
- 启动或创建排行榜层时先应用本地缓存。
- 榜单刷新后比较 `remoteProfile.updatedAt` 与本地 `savedAt`：远端更新时接受远端，否则继续保留本地短期权威。
- 给本地权威设置 TTL，避免永久压住跨设备更新。

典型症状与修复：
- **保存时 UI 成功，下次打开重置**：缺少本地资料缓存，或 update/get 使用不同云环境；补本地缓存与 `updatedAt` 比较。
- **第一次进入有榜单，点击刷新变空**：`forceRefresh` 重算路径失败或查错集合；刷新失败/空结果要回退非空缓存。
- **保存资料后榜单行仍旧头像昵称**：缓存条目没有同步 profile，或客户端没有把本次提交覆盖到当前用户行。
- **云函数 500**：先看云函数日志；常见是集合名前缀错、doc update 目标不存在但没 set、`FROM_OPENID` 没取、缓存写失败未隔离、索引/权限错误。

## Canvas 资料编辑 UI

小游戏没有 DOM，资料弹窗通常是 Canvas 自绘。需要原生授权按钮时：
- 用 `wx.createUserInfoButton` 创建透明按钮，位置覆盖 Canvas 头像区域。
- 只在资料弹窗可见且未授权时显示。
- 弹窗关闭、层隐藏、用户已授权后必须 hide/destroy，避免透明按钮拦截其它 Canvas 交互。
- 已授权后打开弹窗可以静默预填微信资料，但只补空字段，不覆盖用户手动输入。
- 点击昵称不要依赖旧版昵称授权，优先用 `wx.showModal({ editable: true })` 让用户手动编辑；保存时读取最新输入，不要提交旧草稿。

头像展示：
- 榜单行和资料弹窗都要支持 `avatarUrl: null`，没有头像时画空头像占位。
- 远程头像用统一图片加载封装，加载失败时保留占位，不阻塞排行榜。
- 云存储上传后优先取临时 URL；如果不可用，按业务判断是否可直接存 fileID。

## 微信头像与相册头像

微信头像路径：
- 未授权时用透明 `createUserInfoButton` 覆盖头像区，引导用户授权。
- 已授权后可用 `wx.getUserInfo` 刷新微信头像；失败时给出“请同意头像昵称授权后重试”等明确提示。

相册路径是可选能力，真机坑较多：
- 优先调用真实相册 API（通常 `wx.chooseImage`，必要时回退 `wx.chooseMedia`），让微信自己触发隐私弹窗。
- 只有相册 API 明确返回 privacy/scope 类失败时，才补调 `wx.requirePrivacyAuthorize` 并重试。
- 将“已授权/无需授权”的 privacy 返回识别为可继续；不要把 `not authorized` 误判为成功。
- 如果产品临时隐藏相册入口，建议注释菜单项和 `tapIndex` 分支，保留底层函数，便于恢复。

隐私错误文案要区分：
- 未在微信后台声明隐私用途：提示去后台配置。
- 用户拒绝/取消：提示重新点击并同意。
- 已授权/无需授权：继续走相册选择，不要中断。
- 普通取消相册：返回 null，不弹错误。

## 部署清单

改排行榜/资料功能后至少检查：
- 云函数：更新、读取、共修榜、加入小组等相关函数是否部署到目标云环境。
- 集合：所有集合名是否带项目前缀，客户端文档与云函数常量是否一致。
- 权限与索引：Top N 排序字段、分数过滤字段是否可查询。
- 客户端云模式：共享云环境和原生云环境开关是否符合当前发布目标。
- 构建产物：小游戏构建后是否把 `cloudfunctions/`、`game.json`、`project.config.json` 复制到输出目录。
- 真机验证：保存资料、关闭重开、点击刷新、无头像占位、授权取消、授权同意都要测。

## 最小排查顺序

1. 确认用户操作是否真的调用到对应客户端 service。
2. 确认 service 调用的云函数名、云实例模式、环境 ID。
3. 看云函数日志，优先定位 500。
4. 直接检查用户主集合文档是否写入。
5. 检查缓存集合是否同步，缓存失败是否影响主写入。
6. 检查客户端是否被旧缓存覆盖，必要时加本地 savedAt/updatedAt 仲裁。
7. 最后再调 UI 展示和按钮命中区域。
